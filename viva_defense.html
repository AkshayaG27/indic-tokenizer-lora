1. The Akshara Structure & The Unicode Trap

Indian scripts (Devanagari, Telugu) are abugidas structured into syllables: $$\text{Akshara} = C_1 + (\text{Virama} + C_2)^* + \text{Matra} + \text{Anusvara}$$ Standard regexes (`\p{L}+`) match only letters, stopping before combining marks $\p{M}$. Because BPE forbids merges across chunk boundaries, matras fall back to raw UTF-8 bytes, causing Telugu fertility to explode to **14.45 tokens/word** in `cl100k_base`.

2. Grapheme-Aware Pre-Tokenization

Our surgical regex: $$(?:\p{L}[\p{M}\u200c\u200d]*)+$$ binds base consonants and all succeeding vowel signs/viramas into atomic chunks. Eliminates the Unicode Trap and restores Telugu token fertility to **2.07 tokens/word** (1.00× Parity).

3. Shannon Entropy & Bits-Per-Byte

Surprisal normalized by raw uncompressed UTF-8 bytes: $$\text{BPB}(s) = \frac{\sum_{i=1}^N -\log_2 P(t_i)}{\text{Total UTF-8 Bytes of } s}$$ Our custom BPE achieves **1.02 BPB** on Indic text vs **4.54 BPB** for `cl100k_base`.

4. Embedding Table RAM & The Pareto Knee

Embedding matrix RAM footprint: $$\mathcal{M}_{\text{embed}} = |V| \times d_{\text{model}} \times b_{\text{param}}$$ Expanding vocabulary from $512 \to 4\text{K}$ reduces fertility by $4.53$ with $+14.0\text{ MB}$ RAM. Beyond $4\text{K}$, frequent syllables are atomic; marginal compression drops to $0.36$, making $|V| = 4\text{K}$ the optimal Pareto knee.

5. LoRA Parameter Decomposition

For frozen base weight $W_0 \in \mathbb{R}^{d \times k}$: $$W = W_0 + \frac{\alpha}{r} B A \quad (B \in \mathbb{R}^{d \times r}, A \in \mathbb{R}^{r \times k})$$ With $r=8, \alpha=16$. Initializing $B=0$ and $A \sim \mathcal{N}(0, \sigma^2)$ guarantees $\Delta W = 0$ at step 0, training only **0.3414%** of parameters.

6. The Embedding Misalignment Trap

Plugging a custom tokenizer into a frozen pre-trained model corrupts learned coordinate mappings. We maintain strict decoupling:

  • Track A: Tokenizer audit & Pareto mapping.
  • Track B: SFT on base SLM using its native pre-trained tokenizer with prompt loss masking (`labels = -100`).

The Akshara Orthographic Structure: Unlike Latin scripts (linear sequences of independent letters), Indian scripts (Devanagari, Telugu) are alphasyllabaries (abugidas) where text is organized into syllable clusters called Aksharas: $$\text{Akshara} = C_1 + (\text{Virama} + C_2)^* + \text{Matra} + \text{Anusvara}$$
The "Unicode Trap" Mechanics
In the Unicode standard:
  • Base consonants belong to category \p{L} (Letters).
  • Dependent vowel signs (matras) and viramas belong to category \p{M} (Combining Marks).

INDIC_GRAPHEME_REGEX = r"(?i:'s|'t|'re|'ve|'m|'ll|'d)|(?:\p{L}[\p{M}\u200c\u200d]*)+|\p{N}{1,3}|..."
By explicitly binding \p{L} and all following combining marks [\p{M}\u200c\u200d]* into an unbreakable chunk, the Akshara remains intact throughout BPE training, reducing Telugu fertility to $2.07\text{ tokens/word}$ (1.00× Parity).

Examiner Solution & First-Principles Defense Verified
Whiteboard Formulation: Bits-Per-Byte (BPB)
Under Shannon's source coding theorem, the uncompressed information content (surprisal) of a token sequence $t_1, \dots, t_N$ is $\sum_{i=1}^N -\log_2 P(t_i)$ bits. We normalize total surprisal by the raw uncompressed string length in UTF-8 bytes: $$\text{BPB}(s) = \frac{\sum_{i=1}^{N} -\log_2 P(t_i)}{\text{Total UTF-8 Bytes of } s}$$ Lower BPB indicates higher subword information density. Our Custom Grapheme BPE achieves $1.02\text{ BPB}$ on Indic text, compared to $4.54\text{ BPB}$ for cl100k_base.
The Embedding Table Memory Trade-off: The physical RAM occupied by the token embedding matrix is: $$\mathcal{M}_{\text{embed}} = |V| \times d_{\text{model}} \times b_{\text{param}} \quad \text{bytes}$$ For $d = 2048$ with 16-bit weights ($b = 2\text{ bytes}$):
  • $|V| = 512 \implies 2.0\text{ MB}$
  • $|V| = 1\text{K} \implies 4.0\text{ MB}$
  • $|V| = 4\text{K} \implies 16.0\text{ MB}$
  • $|V| = 32\text{K} \implies 128.0\text{ MB}$
The Pareto Knee: Moving from $512 \to 4\text{K}$ drops Telugu fertility from $6.60 \to 2.07$. Beyond $4\text{K}$, all frequent syllables are already atomic; additional tokens only memorize rare full words, giving diminishing compression while continuously inflating embedding RAM.

In LoRA ($W = W_0 + \frac{\alpha}{r} B A$), why is $B$ initialized to zero while $A$ is initialized from a Gaussian, and what are the exact backpropagation gradients $\frac{\partial \mathcal{L}}{\partial A}$ and $\frac{\partial \mathcal{L}}{\partial B}$?

Both $A$ and $B$ must be initialized to zero; gradients are computed via finite difference numerical approximation.
B

Examiner Solution & First-Principles Defense Verified
Whiteboard Derivation: LoRA Gradient Propagation
For a pre-trained frozen weight $W_0 \in \mathbb{R}^{d \times k}$, LoRA decomposes the update $\Delta W$ into $B \in \mathbb{R}^{d \times r}$ and $A \in \mathbb{R}^{r \times k}$ ($r \ll \min(d, k)$): $$h = W x = W_0 x + \Delta W x = W_0 x + \frac{\alpha}{r} B (A x)$$ Why $B=0$ and $A \sim \mathcal{N}(0, \sigma^2)$? At step $t=0$, $\Delta W = \frac{\alpha}{r} (0 \cdot A) = 0$. The adapter introduces zero perturbation to the pre-trained model at the start of fine-tuning, preventing destructive initial updates.

Matrix Calculus Backpropagation: Let $G = \frac{\partial \mathcal{L}}{\partial h} \in \mathbb{R}^{B \times d}$ be the incoming gradient:
  1. Gradient w.r.t. Adapter Matrix $A$: $$\frac{\partial \mathcal{L}}{\partial A} = \frac{\alpha}{r} B^T G x^T$$
  2. Gradient w.r.t. Adapter Matrix $B$: $$\frac{\partial \mathcal{L}}{\partial B} = \frac{\alpha}{r} G (A x)^T$$
  3. Gradient Backpropagated to Input Activation $x$: $$\frac{\partial \mathcal{L}}{\partial x} = \left( W_0^T + \frac{\alpha}{r} A^T B^T \right) G$$
Base weights remain strictly frozen: $\nabla_{W_0} \mathcal{L} = 0$, training only $0.3414\%$ of parameters.

Evaluation Metrics & Morphological Richness
Why is standard word BLEU unreliable for evaluating Indic language generation, and why is character n-gram F-score (chrF) preferred?
A
Indic languages are morphologically agglutinative where prefixes, case markers, and postpositions fuse into complex words; word-level BLEU penalizes valid inflections as 0-matches, whereas chrF computes character n-gram precision/recall, rewarding correct stem matches.
B
Word BLEU requires texts to be capitalized, which is unsupported by the Devanagari script.
C
BLEU can only be calculated on English translations through Google Translate API calls.
D
chrF is an unsupervised metric that operates without reference target sentences.
Examiner Solution & First-Principles Defense Verified
The Failure of Word BLEU on Agglutinative Scripts: Word-level BLEU measures exact word n-gram matches. In languages like Telugu and Hindi, grammatical case markers (vibhakti) and postpositions fuse directly to the noun stem (e.g., Telugu: పుస్తకము [book] vs. పుస్తకములో [in the book]). If the model generates an inflectional variant that is semantically accurate, word BLEU gives a score of 0.0 for that token!
chrF Formulation (Popović, 2015)
chrF computes the $F_\beta$-score over character n-grams (typically 1 to 6 characters): $$\text{chrP} = \frac{\sum_{n=1}^6 \text{Matched character n-grams}}{\sum_{n=1}^6 \text{Total candidate character n-grams}}$$ $$\text{chrR} = \frac{\sum_{n=1}^6 \text{Matched character n-grams}}{\sum_{n=1}^6 \text{Total reference character n-grams}}$$ $$\text{chrF}\beta = (1 + \beta^2) \frac{\text{chrP} \cdot \text{chrR}}{\beta^2 \text{chrP} + \text{chrR}}$$ Because it operates at the character n-gram level, chrF gives substantial credit when the base lexical stem is generated correctly even if a trailing case marker differs slightly, correlating far higher with human judgment in Indic NLP.

Textbook Rigor: The BPE Containment Invariant
What is the "Containment Invariant" defined in Textbook Chapter 09 (Listing 9.1), and why is it critical for multi-lingual subword tokenizers?
A
Every emitted subword token must be a strict substring of exactly one pre-tokenization chunk; tokens must never cross chunk boundaries or span across punctuation/spaces.
B
The vocabulary size must contain all 1,114,112 possible Unicode codepoints in its initial merge table.
C
All tokens must contain an odd number of bytes to prevent alignment faults in GPU shared memory.
D
The training corpus must contain equal proportions of English, Hindi, and Telugu sentences.
Examiner Solution & First-Principles Defense Verified
The Containment Invariant (Chapter 09, Listing 9.1)
Let $s$ be a raw text string, and let $\mathcal{P}(s) = [c_1, c_2, \dots, c_K]$ denote the pre-tokenization partition emitted by the regex. Let $\mathcal{T}(s) = [t_1, t_2, \dots, t_N]$ denote the final subword tokens emitted by the BPE model.

The Containment Invariant: $$\forall t_i \in \mathcal{T}(s), \quad \exists ! c_j \in \mathcal{P}(s) \quad \text{such that} \quad t_i \sqsubseteq c_j$$ (Every token $t_i$ must be a strict contiguous substring $\sqsubseteq$ of exactly one pre-tokenization chunk $c_j$).

Why it matters: If merges were permitted across pre-tokenization chunks, common punctuation marks (e.g. periods, commas) or whitespace could merge with preceding words (e.g. `"done."` or `"book "`), artificially doubling vocabulary size and destroying compositionality across languages.

Question 9
Data Integrity: Unicode Normalization (NFC vs. NFD)
Why must raw Indic text be normalized using Unicode Normalization Form C (NFC) prior to BPE pre-tokenization in `src/tokenizer/unicode_regex.py`?
A
Indic text can represent the same visible glyph as either a precomposed single codepoint (NFC) or decomposed multi-codepoints (NFD); failing to normalize fragments vocabulary counts across multiple distinct token IDs for identical words.
B
NFC converts all Devanagari characters into ASCII characters to reduce memory consumption.
C
NFD is forbidden by the Python 3.10 standard library due to memory leaks.
D
NFC automatically translates Telugu sentences into Hindi before BPE merges.
Examiner Solution & First-Principles Defense Verified
The Canonical Equivalence Dilemma in Unicode: In Indian scripts, many visual glyphs can be encoded in two distinct byte sequences:
  • NFD (Canonical Decomposition): Base character followed by separate combining marks. For example, Devanagari क़ encoded as U+0915 (क) + U+093C (Nukta ़).
  • NFC (Canonical Composition): Single precomposed composite codepoint U+0958 (क़).
To a human, both look identical on screen. But to a naive byte or subword tokenizer, they represent two completely different byte streams!

If unnormalized, the BPE algorithm allocates two separate token IDs for the exact same word depending on whether the source document was typed on an Android keyboard or Windows InScript keyboard. Enforcing normalize_unicode(text, "NFC") ensures canonical deduplication.

LoRA Architecture: Why Target `q_proj` and `v_proj`?
Why did your LoRA configuration target specifically `q_proj` and `v_proj` rather than adapting all linear projection layers in the transformer?
A
Adapting $W_q$ alters attention routing while adapting $W_v$ alters feature representation; this combination captures maximal task adaptation with only 460,800 parameters (0.3414%), strictly satisfying the parameter budget invariant (< 1.0%).
B
PyTorch PEFT raises an internal compilation error if `k_proj` or `o_proj` are included in `target_modules`.
C
Adapting feedforward layers forces the base model to forget all English pre-training knowledge.
D
The key projection matrix $W_k$ contains only frozen RoPE sinusoidal constants, so its weights cannot be modified.
Examiner Solution & First-Principles Defense Verified
The Minimal Sufficient Adaptation Subspace (Hu et al., 2021)
In the foundational LoRA paper, the authors benchmarked adapting different weight subsets across attention and MLP layers:
  • Adapting $W_q$ alone: Captures which tokens to attend to, but lacks the capacity to transform output representations.
  • Adapting $W_v$ alone: Transforms semantic features, but cannot steer attention heads toward new syntactic patterns.
  • Adapting both $W_q$ and $W_v$: Achieves over 95% of the performance of adapting all projection weights ($W_q, W_k, W_v, W_o, W_{\text{mlp}}$) while keeping trainable parameters under 0.35%.
In our model, adapting `q_proj` and `v_proj` requires only $460,800$ weights ($1.75\text{ MB}$ memory footprint), strictly satisfying AC-5 ($< 1.0\%$ budget) and enabling rapid training on consumer hardware without GPU out-of-memory errors.
